# 동시성 폭이 스텝의 무엇을 바꾸는가 — C=2 가 1.23× 인 이유와, 그것을 바꾸려면 무엇을 바꿔야 하는가

> 2026-09-16. `STEP_KERNEL_MAP.md` 는 **C=1 스텝이 무슨 커널로 이루어지는지**를 적는다. 이 문서는 그
> 위에 축을 하나 더 얹는다 — **폭이 늘면 그 커널들이 각각 얼마나 자라는가.** 여기 있는 배수는 전부
> 한 실행 안에서 잰 것이고, 모델이라고 적은 것은 잰 것이 아니다.

## 요약

동시 요청을 둘로 늘리면 토큰은 2배가 되는데 처리량은 **1.23배**만 된다. 그 손실의 **89%가 MoE 한
군데**다. 그리고 MoE 가 자라는 이유는 일의 양이 아니라 **가중치를 읽어야 하는 서로 다른 전문가 수**다.
288 전문가 top-8 에서 토큰 하나는 전문가 8개를 끌고 오고, 두 시퀀스가 같은 전문가를 고를 일은 거의
없다. 그래서 **나눠 쓸 자원이 생기지 않는다** — 이것은 스케줄링 문제가 아니라 라우팅 문제다.

## §1 잰 것 — 폭이 커널별로 얼마나 자라는가

프로덕션 srv2, `POST /v1/engine/profile` 24 스텝씩, C=1 은 요청 하나 · C=2 는 동시 둘.
CUPTI 합이라 **절대값은 PDL 겹침으로 과대**하다(one-shot 항목 참조: 같은 부팅의 배치 이벤트는
8행 31.7~33.2 µs 를 말한다). 유효한 것은 같은 실행 안의 **비율**이다.

```
device_us_per_step    C=1 59,301      C=2 80,342      1.355×
```

| 커널 그룹 | C=1 µs | C=2 µs | 배수 | 증가분 |
|---|---:|---:|---:|---:|
| **MoE static v5** | **25,212** | **44,027** | **1.75** | **18,815** |
| dense rows16 (C=2 전용) | 0 | 6,111 | — | 6,111 |
| mHC | 4,616 | 6,241 | 1.35 | 1,625 |
| input pack | 1,969 | 3,309 | 1.68 | 1,340 |
| one-shot AR | 3,000 | 3,949 | **1.32** | 949 |
| KDA gated delta | 675 | 1,048 | 1.55 | 373 |
| `_commit_layers` | 334 | 658 | 1.97 | 324 |
| `k_publish_packets` | 1,864 | 2,157 | **1.16** | 293 |

전체 증가분 21,047 µs 중 **MoE 가 18,815 µs (89%)**. 통신(1.32×)과 패킷(1.16×)은 오히려 잘
상각된다 — 원장의 C=2 분해가 MoE·통신·mHC 를 나란히 놓았는데, **실제로는 MoE 가 압도한다.**

`dense rows16` 이 C=2 에만 나타나는 것은 밀집 쪽에 **C=2 전용 열여섯 행 경로가 실제로 서빙되고
있다**는 확인이다(`mk_run_gemm_rows16`, 셀 표는 `dense.bound_input_cell` 의 16/24/32,
`st_c2_dense_cells_20260915` 에서 측정). 밀집은 이미 폭을 나눠 쓴다.

## §2 왜 MoE 는 1.75× 인가 — 커널의 회계가 그렇게 적혀 있다

`moe_static_kernel_v4` 의 라우팅 단계는 작업 항목을 이렇게 센다:

```python
if row % tile_m == 0:                       # tile_m = 32 (v4 는 32 고정)
    next_item += output_tile_count_n
```

즉 **항목 = Σ_전문가 ⌈행수_e / 32⌉ × n블록**. 디코드는 전문가당 행이 대개 **1개**이므로
`⌈1/32⌉ = 1` — **항목 수가 서로 다른 전문가 수에 정비례한다.** 행이 몇 개든 전문가를 하나 건드리면
32행짜리 m-타일 하나가 통째로 선다.

그러면 폭이 늘 때 비용은 "라우팅된 행"이 아니라 "**건드린 전문가**"를 따라간다. 균일 라우팅 가정에서
슬롯 s 개가 288 전문가를 때릴 때 서로 다른 전문가는 `288(1 − e^(−s/288))` 이다 — **이 줄은 모델이다.**

| | 슬롯 (행 × top-8) | distinct (모델) | 비율 |
|---|---:|---:|---:|
| C=1 | 8 × 8 = 64 | 57.4 | — |
| C=2 | 16 × 8 = 128 | 103.4 | **1.80** |

**모델 1.80, 측정 1.75.** 웨이브 양자화까지 넣으면(`mac = 48` 상주 CTA, 항목 ≈ 2×distinct)
C=1 은 ⌈115/48⌉ = 3 웨이브, C=2 는 ⌈207/48⌉ = 5 웨이브로 1.67 — 측정값은 그 둘 사이에 앉는다.

### 옛 C=4 기록과도 맞는다

850차(`#838 §3` 스테이지 표, CUDA 이벤트, 2K)는 **rows1 47.7 ms → rows4 110.8 ms**,
`decode_ms_per_row = 21.03` 을 기록했다. 선형으로 풀면 **고정 26.6 ms + 행당 21.03 ms**,
C=4 배수 = 4×47.7/110.8 = **1.72**. K=6 시절이니 C=1 은 7행 56 슬롯, C=4 는 28행 224 슬롯:

```
distinct  C=1 50.7    C=4 155.8    비율 3.07 / 토큰 4배  →  MoE 배수 1.30
```

MoE 1.30 과 잘 상각되는 나머지의 가중 평균이 전체 1.72 다. **C=2 에서 맞춘 모델이 C=4 기록도
설명한다.**

### 패딩의 크기

전문가당 1행에 m-타일 32행이면 **행 슬롯의 32분의 1만 실제 토큰**이다. C=1 은 실토큰 64개를 위해
57.4 × 32 ≈ 1,836 행 슬롯을 세운다. 이 낭비는 폭을 늘려도 줄지 않는다 — 전문가가 늘 뿐이다.

## §3 왜 나머지는 잘 상각되는가

- **one-shot AR**: 8행 31.7~33.2 µs → 16행 45.5~45.9 µs. 일이 2배인데 1.32~1.38× — **행당으로는
  4.15 → 2.87 µs 로 31% 싸진다.** 고정비(배치 이벤트 기준 바닥 ~30 µs = 고정 16 + 직렬화 14,
  `stkernel-oneshot-comm-wait`)가 두 배의 토큰에 나뉘기 때문이다.
- **k_publish_packets** 1.16×, **mHC** 1.35×: 같은 이유. 이들은 폭이 늘수록 이득이다.
- **dense**: C=2 전용 경로가 있어 `st_c2_dense_cells_20260915` 가 "C2 가 쌈" 이라고 적었다.

**폭을 늘려서 손해 보는 것은 MoE 하나다.**

## §4 안 되는 것 — 그리고 왜 안 되는지

"하이퍼스레딩처럼 공유자원을 쓰자" 는 발상은 **같은 실행 유닛을 두 스레드가 나눠 쓴다**는 전제 위에
선다. 여기서는 토큰마다 **다른 가중치 8벌**을 끌고 오므로 그 전제가 없다.

- **라우팅 인지 배칭**(전문가가 겹치는 시퀀스를 같이 돌린다) — 겹칠 것이 없다. 아래 §4.1.
- **핫 전문가 상주**(자주 뽑히는 전문가를 붙들어 둔다) — 상주시킬 핫 집합이 없다. 아래 §4.1.
- **타일을 여러 전문가가 공유** — m-타일 하나는 **전문가 하나의 가중치**를 읽는다. 전문가를 섞으면
  가중치를 섞어야 해서 타일의 정의가 깨진다.
- **tile_m 을 줄인다** — `_parse_glm53_static_v2` 가 `tile_m != 32` 를 거부한다(v4 의 MMA M).
  줄일 수 있다 해도 낭비는 32× → 8× 로 줄 뿐, **전문가 수에 비례하는 항은 그대로다.**

### §4.1 디코드 규모의 실 라우팅은 거의 균일하다 (추론, 미실측)

쏠린 분포라면 C=1 과 C=2 가 거의 같은 전문가 집합을 때려 배수가 **1.0 쪽으로** 내려간다. 균일하면
1.80. **측정은 1.75** 다. 그러니 이 규모에서 쏠림이 벌어주는 것은 3% 남짓이고, 배칭·상주 레버는
붙잡을 구조가 없다.

14차 조사의 `max 2,296 · median 40 · 활성 216` 은 **프리필 규모**(수천 토큰) 통계다. 디코드의
64 슬롯에서는 그 꼬리가 나타나지 않는다.

**이것은 추론이다.** 확정하려면 MoE 캡처를 켠 부팅으로 라우팅 id 를 세야 한다 — 오늘 캠페인은
head 채널만 켰다(`stats.jsonl`: `"on": {"moe": false, …, "head": true}`), 그래서 `ids/` 가 비었다.

## §4.2 이 기계는 인오더 단일 스트림이다 — 그리고 듀얼 이슈는 C=2 에 없다

CPU 로 치면 상주 CTA 48 이 발행 폭이고, 작업 항목이 μop 이며, 웨이브가 발행 그룹이다(C=1 항목
≈115 → 3 웨이브, C=2 ≈207 → 5). 부분 발행 낭비도 그대로 있다 — 115/48 = 2.4 인데 3 을 낸다.
그러나 **이 기계는 발행 폭에 막힌 것이 아니라 채움에 막혀 있다**: 항목 하나가 전문가 가중치 타일을
HBM 에서 통째로 끌어와 1행을 계산한다(§2). 모든 μop 이 L1 을 놓치고 DRAM 까지 가는 루프를 발행
폭으로 고칠 수 없는 것과 같다.

중첩은 어떤가. `engine/profiles/glm53/execution.py` 가 첫 문장에서 못박는다:

> *Compute kernels share one stream and their existing workspaces. **Only the TP reduction stream
> overlaps them**: two C=4 groups execute in the same fixed order on every rank. This is operation
> scheduling, not concurrent model replays.*

연산 커널은 **스트림 하나에 인오더**다. 듀얼 이슈에 해당하는 장치는 `ExecutionPlan.overlap` 하나뿐이고:

```python
def groups(self, sequences):
    return ((0, 2), (2, 4)) if self.overlap and sequences == 4 else ((0, sequences),)
```

배치를 둘로 쪼개 한 그룹의 집합통신을 다른 그룹의 연산 밑에 숨긴다. 세 가지가 걸린다:

1. **`sequences == 4` 에서만 정의된다.** C=2 에는 경로 자체가 없다.
2. **꺼져 있다** (`tp_overlap=0`).
3. **이미 채택한 둘과 상호배타다** — `direct_mhc`(프로덕션 1)와 `deferred_kda`(#937 기본값 on,
   `deferred_kda_workspace_bytes` 가 비어 있지 않다)가 각각 `overlap` 과 함께 `ValueError` 를 낸다:
   전자는 쪼개지 않은 같은 스트림 집합통신을, 후자는 쪼개지 않은 타깃 행과 단일 커밋을 요구한다.

**그리고 C=2 에서는 이 수법이 원리적으로 손해다.** 그룹이 (0,1),(1,2) 로 갈리면 각 그룹이 자기
전문가 집합을 따로 적재하므로, §2 의 비용식에서 distinct 가 두 번 계산된다. C=2 가 안 늘어나는 바로
그 성질이 **중첩도 막는다.** 통신을 숨겨 버는 것보다 전문가를 두 번 읽어 잃는 것이 크다.

## §5 남는 것 — 무엇을 바꿔야 폭이 값을 하는가

전부 **라우팅을 바꾸는** 쪽이다. 순서는 값/비용이다.

1. **디코드 top-k 를 줄인다.** 슬롯이 직접 줄어든다: top-8 → top-4 면 C=1 슬롯 64 → 32,
   distinct 57.4 → 30.2, **MoE ≈ 0.53×** — MoE 가 스텝의 42% 이니 전체 약 **−20%**(모델).
   폭에 따라 k 를 바꾸면(`k = 8/C`) 슬롯이 상수가 되어 MoE 가 폭에 대해 공짜가 된다는 계산도 나온다.

   **그러나 이것은 노브가 아니라 캠페인이다.** 두 층에서 막힌다.

   *엔진*: `_is_admitted_tp_geometry` 가 `num_topk == cell.topk` 를 요구하고, 그 셀은 docstring 이
   적은 대로 **top-8** 이다. 게이트가 떨어지면 `_static_v2_config_for` 가 `None` 을 돌려주고 **정적
   v2 레인이 통째로 꺼져 스톡 커널로 내려간다**(38차: v2 는 스톡 대비 +9.7~11.6%). 게다가 **조용히**
   떨어진다 — 같은 docstring 이 "the first v2 probe measured the stock kernel six times over" 라고
   그 전례를 적어 두었다. 이 문서의 §2 분석(항목·tile_m·직접 스캐터)은 전부 v2 레인의 것이라
   스톡에서는 성립하지도 않는다. 직접 스캐터의 기하 검사에는 `num_topk == 8` 이 리터럴로 들어 있다.

   *모델*: 라우터는 top-8 로 훈련됐다. `norm_topk_prob` 재정규화는 빠진 전문가 몫을 상위 k 개로
   대체하고, `routed_scaling_factor` 와 **항상 켜지는 공유 전문가 1개**와의 비율도 함께 움직인다.
   훈련에서 본 적 없는 영역이다.

   그래서 순서는 **품질부터**다. 그 비용을 잴 채널이 오늘 생겼다: head NLL
   (`measurements/st_hybrid_recalibrated_head_nll_20260916`, 대조군 `ARMA.head.jsonl` 133 문서).
   손실이 작으면 적응형이 아니라 **그냥 낮은 k 를 쓰면 된다**(C=1 도 같이 싸진다). 손실이 크면
   적응형만 남는데, 그때는 "부하 중 품질 저하"를 받아들일지가 운영 판단이다 — 같은 입력이 서버가
   바쁠 때 더 나쁜 답을 내고 재현성이 깨진다. 그리고 드래프터 수용률이 타깃 분포에 붙으므로
   tokens/step 이 함께 움직일 수 있다(미측정).
2. **포화까지 폭을 올린다.** distinct 는 슬롯이 288 을 크게 넘어야 포화한다. C=4 도 슬롯 256 으로
   59% 포화라 배수가 1.72 에 그쳤다(§2). 유의미한 상각은 C≈16 이상인데 KV 예산과 `max_seqs=4` 가
   막는다. **이 방향은 지금 닫혀 있다.**
3. **전문가당 가중치를 줄인다**(더 작은 전문가, 더 공격적인 양자화). MoE 가 가중치 적재에 묶여
   있으므로 바이트가 곧 시간이다. 오늘의 다른 결과가 여기 붙는다 — 가중치오차 1.5~1.8× 가
   head NLL 에서 0.03 nats 를 못 만들었다(같은 measurements 항목). **팩 오차가 헤드에 싸다면
   더 공격적인 양자화를 감당할 여지가 있다**는 뜻이고, 그것은 MoE 시간에 직결된다.

## §6 안 잰 것

- **라우팅 분포 실측**(§4.1 은 추론). MoE 캡처를 켠 부팅 한 번.
- **top-4 팔**의 속도·품질. §5.1 의 수치는 전부 모델이다.
- **서빙 판정 없음.** §1 은 프로파일러 하의 비율이고 C=1 step/s 판정 채널이 아니다.
- 오늘의 bench-dec 배수 **1.257(디코드 1.233)은 `valid=False`** 다 — 두 레그가 측정 중에 JIT 를
  물었고, C=1 이 더 많이 물어(특수화 +4 대 +2) **배수가 위로 편향**돼 있다. 진짜 배수는 더 낮다.
- `dense.wide_input_cell` 은 폭 **14/21/28**(K=6 의 C=2/3/4)에 남아 있어 K=7 서빙 폭
  16/24/32 와 만나지 않는다. bound 가 아닌 갈래의 그 셀들은 현재 도달 불가다. 값은 작다 —
  `dense rows16` 이 C=2 전체의 7.6% 뿐이다.
