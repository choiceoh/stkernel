# ST 엔진 메모리 최적화와 OOM 방지 — 탐구 (2026-09-11 밤, main 98517db1 + PR #552)

코드(`engine/base`, `profiles/glm53`, 런처, earlyoom 설정), 원장 26·39·40·45차, 그리고 **지금 srv4 에서
다른 세션이 띄워 둔 45층 부팅**의 실측으로 정리했다. GPU 실험은 하지 않았다(플릿 사용 중).
"실측" 은 오늘 이 상자에서 읽은 값, "원장" 은 MEASUREMENTS.md 의 과거 실측, "계산" 은 프로필 코드로 계산한 값이다.

## 1. 판정

**남은 위험은 상주 크기가 아니라 과도(transient)와 이웃이고, 그것을 보는 눈이 서빙 중에 없다.**

지금 srv4 실측: 45층 랭크 하나가 **58.0 GiB**(계산한 아레나 56.0 + 컨텍스트·NCCL), 이웃까지 더해
MemAvailable **40.2 GiB**. earlyoom 의 SIGTERM 선은 **절대 6 GiB** 이므로 여유는 **34 GiB**.
그런데 원장 40차에는 *설명되지 않은* 8K 프리필 순간 **20 GiB+ 일시 사용**이 두 번의 earlyoom 과 함께 적혀 있다
(4065행, KDA 부팅의 프리필 웜업). 프리필의 모양은 서빙에서도 같고, 그때 제안된 계측("4 노드 메모리 감시")은
26차에 조사용으로 **엔진 밖에 1초 샘플러를 임시로 심은 것**이 전부였다 — 엔진 안에는 남지 않았다. 26차의 결론은 더 날카롭다 —
**"전부 이 절벽에서 몇백 MiB 차이로 살거나 죽었다."**

즉 34 GiB 의 여유는 넉넉해 보이지만, 그 여유를 먹는 항이 측정된 적이 없고, 상자를 공유하는 이웃은 시시각각 변한다
(오늘만 해도: 프로덕션 vLLM 74 GiB → 내 스모크가 죽임 → 재기동 → 지금은 다른 세션의 ST 58 GiB).

## 2. 이 상자의 OOM 물리 — 모든 방안이 여기서 갈린다

| 사실 | 출처 | 따라 나오는 것 |
|---|---|---|
| earlyoom 은 **절대 6 GiB**(SIGTERM) / 4.5 GiB(SIGKILL), swap 비구속 | `/etc/default/earlyoom` | 방어는 "MemAvailable 을 6 GiB 위로" 하나의 문장으로 환원된다 |
| 커널 min watermark **4.0 GiB**: 그 아래는 fork 도 ssh 도 안 되는 웻지 | earlyoom 설정 주석(srv3 OOM 덤프) | 6 GiB 선은 웻지 회피용이지 여유가 아니다 |
| **엔진이 고의로 1순위 사살 대상**(`--prefer VLLM::Worker\|vllm\|pt_main_thread\|python3`) | 같은 파일, 2026-09-04 세 노드 웻지 뒤 | `oom_score_adj` 로 피하려 들면 09-04 웻지를 되살린다 |
| NVRM 페이지는 **핀**됨 — 드롭도 스왑도 안 된다 | 같은 파일 | 일단 잡은 메모리는 죽기 전엔 못 돌려준다 |
| 아레나는 **한 할당 + 범프**: 블록을 비워도 OS 로 안 돌아간다 | `base/arena.py` | 부팅 뒤 엔진의 발자국은 **상수**. 런타임 축소 방안은 존재할 수 없다 |
| GB10 캐싱 할당자는 churn 에서 해제 블록을 재사용하지 않고 **새 페이지를 매핑** — 산 텐서 +0.2 GiB 에 예약 +14.5 GiB | 원장 26차 계측 | **예약−할당 간극은 캐시가 아니라 이 기계에선 잃은 메모리**. 감시 대상은 `memory_reserved` 다 |
| 워커 RSS 7 GiB 뿐이라 `ps` 로는 아무것도 안 보였다 | 원장 26차 | 호스트 도구는 이 엔진의 발자국을 못 본다. 계측은 엔진 안에 있어야 한다(D1 의 이유) |
| 26→5 GiB 낙하에 **4 초** | 원장 26차 궤적 | 감시 주기는 5 초가 아니라 **스텝마다**여야 한다 |

## 3. 지금 있는 방어와 구멍

| 층 | 있는 것 | 구멍 |
|---|---|---|
| 부팅 입장 | `prepare_allocation`(파일 캐시 버리기 + 회수 펌프 + MemFree ≥ 아레나+16 GiB + TP 투표), `RuntimeMemory`(할당자 바이트 상한 = 아레나+12 GiB, 물리 여유 검사) | 플릿 부팅으로 미검증. **이웃을 예산에 세지 않는다**(dsv41 예산엔 `tenants` 줄이 있고 glm53 엔 없다) |
| 부팅 준비 | 최대 프리필 2회 + 모든 그래프 형상의 예약 피크를 원장에 기록(#549) | 합성 입력·선언 청크에 한정. 서빙 중 실형상은 미측정 |
| 서빙 | **없다** | 매 스텝 메모리를 보지 않는다. 이웃이 자라도 엔진은 계속 입장시킨다 |
| 과도 상한 | 할당자 바이트 상한이 예약을 묶고, 상한에 닿으면 파이토치가 캐시를 비우고 재시도 → **간극 누수의 자동 청소기 역할** | 상한이 *총량의 분수*라 이웃이 커져도 안 줄어든다. 엔진은 자기 상한 안에서 상자를 6 GiB 아래로 밀 수 있다 |
| 실패 처리 | 예외 → `_abort()` → 엔진 전체 정지, 모든 클라이언트 503 | 과도한 요청 **하나**가 엔진 전체를 죽인다. `OutOfMemoryError` 를 따로 잡는 곳이 없다 |
| 사후 | 슈퍼바이저 30 s 헬스 → 포렌식 → 재기동(백오프 60 s ×2 ≤ 30 min), 사망 덤프(D12) | 복구는 있다. 예방이 없다 |

## 4. 바이트는 어디에 있나 — 그리고 무엇이 움직이나

랭크 하나, 계산값(45층 + DFlash2):

| 항목 | GiB | 압축 가능? |
|---|---:|---|
| 전문가 packed (NVFP4 nibble) | 35.44 | **아니다** — 체크포인트 형식 그대로 |
| 전문가 스케일 (e4m3/16) | 4.43 | **아니다** — packed 의 12.5%는 group-16 의 정의 |
| 그 밖 bf16 (KDA 2.23 / MLA 0.73 / dense·shared 0.70 / embed·head 0.59 …) | 4.63 | 억지 W4A16 은 **운영자 금지** |
| 드래프터 (랭크마다 통째) | 2.18 | TP 분할로 −1.6 가능하나 드래프트 경로에 콜렉티브가 붙는다. 프로덕션도 DRAFT_TP=1 |
| 상태 슬롯 247 MiB × (max_seqs+1) | 1.21 | **아니다**(아래 설명) |
| prefix 스냅샷 75 MiB × 8 | 0.59 | 개수는 선택 |
| 페이지드 KV (선언 8.73 중) | 7.52 | 선택 |

**슬롯 247 MiB 가 왜 안 줄어드나** (204 MiB 가 재귀 링): 수용 개수는 헤드를 지난 **뒤**에야 알 수 있으므로
K+1 개 상태는 포워드 전체에 걸쳐 살아 있어야 한다. 층별 스크래치로 바꾸면 n×6×34 MiB 가 필요해 이득이 없고,
수용 뒤 재계산은 매 디코드 스텝에 34층 두 번째 패스를 얹는다. dtype 강등도 길이 아니다 —
프로덕션이 이미 **conv bf16 + 재귀 fp32**(원장 4051행)이고 ST 는 같은 형이다. 즉 동시성 1 증가의 값은
**슬롯 247 MiB + 그래프 10개 + 토큰당 6,043 B**이고, 그건 깎는 게 아니라 **사는 것**이다.

**과도**(아레나 밖, 프리필 청크 6,912 · `SELECT_ROWS=1024` 뒤):

| 컨텍스트 | 인덱서 선택 로짓 | 후보 게더 | 잔차 스트림(고정) |
|---:|---:|---:|---:|
| 128K | 0.12 GiB | 0.00 | 0.21 |
| 512K | 0.50 GiB | 0.02 | 0.21 |
| 1M | **1.00 GiB** | 0.03 | 0.21 |

행 수를 고정했으므로 과도가 **컨텍스트에 비례해 자란다**. 바이트 예산으로 바꾸면 상수가 된다(§5-D).

**남는 36.4 GiB**(예산 표의 unassigned)는 낭비가 아니라 **미배정**이다. §2 를 보면 그 대부분은 이미
"이웃과 과도를 흡수하는 몫" 으로 일하고 있다 — 다만 아무도 그렇게 선언하지 않았을 뿐이다.

## 5. 방안 (레버가 큰 순서)

### A. 서빙 중 메모리 감시 — 40차가 요청하고 만들어지지 않은 계측
매 스텝 `/proc/meminfo` 1줄 + `memory_reserved`(≈10 µs, 46 ms 스텝 대비 무시 가능)를 읽어 링에 남기고,
N 스텝마다 원장 줄로 낸다. 감시 대상은 **예약**과 **MemAvailable** 둘(§2 의 "예약−할당 = 잃은 메모리").
죽을 때 사망 덤프에 같이 나간다. **이것이 없으면 아래 전부가 추정이다.**
게이트: 45층 부팅 + onepass 중 랭크별 MemAvailable 최소값과 예약 피크가 원장에 남는다.

### B. 입장 배압 — 상자가 좁아지면 새 요청을 안 받는다
아레나가 못 줄어드는 이상(§2) 유일한 레버는 **안 늘리는 것**이다. N 스텝마다 네 랭크의
`min(device free, MemAvailable)` 를 `all_reduce MIN`(이미 `_settle` 이 쓰는 패턴) 하고,
`floor + margin` 아래면 **입장만 멈추고 디코드는 계속**한다(D10: 돌던 디코더는 보호). 회복되면 재개.
새 요청은 큐에 남거나 503. 비용: 스텝당 콜렉티브 하나(또는 N 스텝마다).
게이트: 이웃을 인위로 키우며 입장이 멈추고 디코더 ITL 이 안 변하는 것.

### C. OOM 격리 — 엔진이 아니라 요청 하나가 죽는다
`torch.OutOfMemoryError` 를 스텝에서 잡아 **랭크 합의 후**(한 랭크만 죽으면 콜렉티브가 어긋난다)
그 요청만 503 으로 떨어뜨리고 `empty_cache()` 하고 계속한다. 지금은 과도한 요청 하나가
전 클라이언트를 끊는다. TP 합의는 §B 와 같은 `all_reduce` 형.

### D. 과도를 바이트로 선언 — `SELECT_ROWS` → 선택 예산
`rows = 예산바이트 // (n_cand × 4)` 로 바꾸면 인덱서 선택 과도가 컨텍스트와 무관한 상수가 된다
(1M 에서 1.00 → 0.13 GiB, 128K 에서는 지금과 동일). 한 줄짜리 변경, 최악의 경우에서 컨텍스트 항을 지운다.

### E. 예산을 정직하게 — 이웃 줄과 헤드룸 줄
`profiles/glm53/budget.py` 에 dsv41 처럼 **`other tenants on this box`**(= total − free, measured) 를 넣고,
남는 36.4 GiB 를 **`headroom for transients and neighbours`(declared, 근거: earlyoom 6 GiB + 원장 26차의 절벽)** 로
선언한다. D1 의 금지("잔여는 측정 대상이 되지 못한다")를 예산 자신에게도 적용하는 것.

### F. 그다음에 지출 — 무엇을 살 것인가 (A·E 뒤, 운영자 결정)
| 지출 | 값 | 비용 |
|---|---|---|
| max_seqs 4 → 8 | 동시 대화 2배 | 슬롯 +0.96 GiB, 그래프 +40개(메모리 미측정 → A 가 답한다), 128K×8 KV 5.90 |
| prefix 스냅샷 8 → 32 | 공유 프리필 재사용 폭 | +1.8 GiB |
| KV 선언 8.73 → N | 더 긴 컨텍스트·더 많은 상주 대화 | 토큰당 6,043 B |
| 나머지는 헤드룸으로 | OOM 여유 | — |

## 6. 하지 말 것 (탐구해서 **버린** 방안)

- **`oom_score_adj` 로 사살을 피하기.** 플릿은 2026-09-04 세 노드 웻지 뒤 **엔진을 1순위 사살 대상으로 고의 설정**했다.
  이유가 파일에 적혀 있다: "바닥을 넘으면 엔진이 폭주자이고, 대안은 노드를 잃는 것인데 그러면 엔진도 잃는다."
  피하게 만들면 대신 죽는 것은 관리면이고, 그게 웻지다.
- **컨테이너 `--memory` 한도.** cgroup 이 NVRM 할당을 세는지 미확인이고, 센다면 실패 모드가
  "컨테이너 OOM-kill" 로 바뀔 뿐 더 낫지 않다. 재는 것이 먼저다(§7).
- **런타임 아레나 축소·부분 해제.** 구조상 불가능하다(한 할당 + 핀). 제안이 다시 나오지 않도록 여기 적는다.
- **재귀 상태 dtype 강등.** 프로덕션과 같은 형(conv bf16 / 재귀 fp32)이라 강등은 프로덕션 이하로 내려가는 것.
- **bf16 잔여 4.63 GiB 의 W4A16.** 운영자 금지.
- **KV 를 NVMe 로 더 내리기.** 이미 D16 이 한다. 전문가 가중치는 매 토큰 뜨거워 대상이 아니다.

## 7. 재야 하는 것 (플릿 창에서, 순서대로)

1. **45층 부팅 관문** — `prepare_allocation` + 아레나 + `RuntimeMemory` 사다리가 4노드에서 지나가나. (지금 다른 세션이
   돌리고 있으니 그 원장 `memory-rank*.json` 을 읽는 것만으로도 절반은 답이 나온다.)
2. **할당 모양** — `probes/engine_alloc_shape_check.py`(plain / expandable / reclaim, 캐시를 채운 뒤).
3. **cgroup 이 NVRM 을 세나** — `--memory 4g` 컨테이너에서 6 GiB CUDA 할당. 2분, GPU 여유 10 GiB 면 충분.
4. **D10 간섭 게이트** — 128K 파킹·복원 중 디코더 p50 ≤ 1.01(`probes/kv_tier_interference.py`, 서브 루프 경로).
5. **서빙 중 실형상 과도** — A 가 붙은 뒤 onepass 한 번. 40차의 "설명되지 않은 20 GiB" 가 여기서 이름을 얻는다.
