# 파킹된 대화의 통째 기록 — 한도 8 은 파킹에서 지켜지지 않았고, 그냥 자르면 루프가 디스크를 읽는다 (2026-09-19)

## 질문

1. `Runner.parked` 는 문서대로 통째 기록 8개(`PARKED_RECORDS_KEPT`)로 묶여 있나?
2. 파킹 때 잘라서 묶으면, 입장·힌트 재확인·재개가 루프에서 기록을 디스크에서 읽게 되나(D10)?
3. 기록 하나는 메모리에서 얼마이고, 프로덕션은 지금 얼마를 들고 있나?

## 결과

**1. 한도는 파킹에서 지켜지지 않았다.** 대화 40개를 파킹하니 전: `Runner.parked` 40개(한도 8), 다이제스트 0개. 후: 8개, 다이제스트 40개.
전에는 티어에서 읽을 때(`_hold_record`)만 잘랐고, 파킹(`park_finish`)은 자르지 않고 넣었다. 그래서 이 프로세스가 파킹한 대화의 기록을
**모든 랭크가** 다 들고 있었다(랭크 1-3 은 훑지 않으니 자를 일도 거의 없다).

**2. 그냥 자르면 루프가 디스크를 읽는다.** 4 랭크, 대화 9개를 파킹한 뒤 대화 0 을 잇는다:

| 트리 | 들고 있는 기록 | 루프가 읽은 기록(랭크마다) | 티어 스레드가 읽은 기록 |
|---|---|---|---|
| 전 | 9 (한도 초과) | 없음 | 없음 |
| 전 + 파킹 때 자르기만 | 8 | **이름으로 잇기: 네 랭크 모두 `[0]`, 힌트로 잇기: 네 랭크 모두 `[0]`** | 없음 |
| 후 | 8 | 없음 | 이름: 네 랭크 `[0]`, 힌트: 랭크 1-3 `[0]`(랭크 0 은 훑기가 막 읽어 둠) |

그냥 자르기만 한 판에서 루프는 `_admit` 의 `parked_record`(context·pending) 와 `_stale_hint` 의 `parked_record`(통째 비교)로 읽는다.
힌트 판에서 랭크 0 도 읽은 까닭: 그 판에서는 파킹이 다이제스트를 지우므로 첫 훑기가 9개 모두의 기록을 다시 읽고(훑기의 읽기
`[0, 1, …, 8]`), 그 읽기가 LRU 를 돌려 훑기가 막 읽은 대화 0 을 도로 밀어냈다. 후에는 훑기가 대화 0 하나만 읽는다(다이제스트는 파킹이 남긴다).

**3. 크기와 비용** (GLM 모양 기록, `engine/profiles/glm53/adapter.py` 의 `park` 와 같은 필드):

| 토큰 | 메모리 | JSON | `json.loads` | `history_head` | `_summary`(파킹 때, 루프) | 힌트 재확인 `_offer_digest` / 전 `_offer` |
|---:|---:|---:|---:|---:|---:|---:|
| 233 | 0.008 MiB | 0.002 MiB | 0.018 ms | 0.001 ms | 0.003 ms | 0.003 / 0.003 ms |
| 43,318 | 1.490 MiB | 0.259 MiB | 3.491 ms | 0.234 ms | 0.385 ms | 0.389 / 0.299 ms |
| 100,000 | 3.431 MiB | 0.597 MiB | 7.222 ms | 0.608 ms | 0.991 ms | 0.926 / 0.826 ms |

토큰당 36 B(파이썬 int 28 B + 목록 칸 8 B). 루프가 새로 하는 일은 파킹마다 `_summary` 한 번(10만 토큰 0.99 ms)과 힌트 재확인의
해시(+0.10 ms). 대신 루프에서 사라지는 것은 들고 있지 않은 기록의 디스크 읽기(10만 토큰 `json.loads` 만 7.2 ms, 디스크 시간 별도).

**4. 프로덕션 GLM-5.3 rank 0 (srv2, 2026-09-19 20:30).** 파킹 223개, KV 토큰 합 147,775(평균 663, p50 233, p90 340, 최대 43,318),
기록 JSON 합 816,593 B. 티어 63.80 / 64 GiB — 대화마다 슬롯 299,932,672 B(286 MiB)가 대부분이다. 블록 4,730,880 B / 768 토큰 =
토큰당 6,160 B. 지금 들고 있는 기록은 147,775 × 36 B ≈ **5.1 MiB** — 작다.

**최악의 경우.** 한 랭크의 대화 티어는 64 GiB 다. 기록 메모리 36 B 에 디스크 6,160 B(+대화마다 슬롯 286 MiB)가 붙으므로, 티어에
들어가는 토큰으로 파킹 기록을 전부 들면 랭크당 최대 64 GiB × 36 / 6,160 ≈ **383 MiB** 까지 간다(20만 토큰 대화면 44개 · 302 MiB).
후에는 통째 기록 8개(20만 토큰이면 8 × 6.9 MiB = 55 MiB)와 대화마다 다이제스트 몇백 바이트다. #687 의 1.04 GiB(280 × 10만 토큰)는
지금의 64 GiB 캡으로는 들어가지 않는 경우다(10만 토큰 대화는 873 MiB 라 75개가 한계).

## 못 잰 것

- GPU·플릿에서 이 커밋으로 부팅하지 않았다. 프로덕션 프로세스의 실제 RSS 도 재지 않았다(위 5.1 MiB 는 토큰 수 × 36 B 계산).
- 시간은 Mac 컨테이너 CPU 의 값이다. GB10(Grace) 에서 `_summary`·`json.loads` 가 얼마인지는 재지 않았다.
- 긴 대화가 몰리는 부하(에이전트 코딩, 10만 토큰 이상)의 프로덕션 모습은 지금 티어에 없다(최대 43,318 토큰).
