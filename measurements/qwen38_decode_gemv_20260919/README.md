# Qwen3.8 디코드 — 라우터의 skinny GEMV, 믹서 사이트 5→3 발사(carry H2), 스텝 A/B (2026-09-19, srv4 단일 GPU 레인)

> 그대로 두는 기록 — 이 날의 단일 GPU 티켓들. 플릿 창 없음(운영자: 추가 창 금지). 뒤 실행은 이 파일을 고치지 않고 새 기록을 남긴다.

운영자 "qwen 최적화. 부팅 말고 디코딩", "전부 머지된 기준으로 해". 모든 티켓은 `bench/fleet.sh run --gpu` 의 단일 GPU 레인
(srv4 GB10, **프로덕션 옆**, 예산 2~4 GiB). 동결 체크아웃은 srv2 `~/st-worktrees/q38step-<sha>`.

## 1. skinny GEMV 대 cuBLAS — `q38gemv-0919c` ([원시](q38gemv-0919c.json))

CUDA 그래프 하나에 16 호출, 가중치를 64 MB 넘게 돌려 L2 밖, 팔 인터리브, 중앙값 9. 이 티켓 동안 프로덕션은 한가했다.

| 모양 [N, K] | 행 | cuBLAS µs (GB/s) | 가장 빠른 설정 µs (GB/s) | 배 |
|---|---:|---:|---:|---:|

| | 8 | 33.6 (78) | 14.2 (185) | 2.37 |
| | 16 | 35.7 (74) | 14.1 (186) | 2.53 |

- cuBLAS 는 한 행에서 gemv 로 대역폭에 닿고 여러 행에서는 못 닿는다(라우터 94→74 GB/s). 1 행과 up 투영은 비긴다.
- 스윕 12 설정의 중앙값은 최선보다 5~9% 뒤 — 타일을 넘어서면 가중치 읽기가 시간이다.
- 같은 레인의 첫 실행 `q38gemv-0919b`(프로덕션이 바빴다)에서는 모든 팔이 느렸고 up 이 36 GB/s 로 보였다 — 경합이지 모양이 아니다.

## 2. 믹서 — 네 발사 대 두 발사(carry H2) — `q38site-0919a` ([원시](q38site-0919a.json)), `q38site-0919b` ([원시](q38site-0919b.json))

사이트 16 개 한 그래프, (down+inject, up) 쌍 13.2 MB 를 돌려가며. µs/사이트, 중앙값 7:

| 행 | cuBLAS 네 발사 (+복사 1) | down 만 skinny (+복사 1) | 게이트를 down 에 (세 발사) | **+ up 에 평균 (두 발사)** |
|---:|---:|---:|---:|---:|
| 1 | 66.5 | 66.5 | 64.6 | **60.3~61.5** |
| 4 | 69.9 | 67.0 | 64.8 | **60.8~61.6** |
| 8 | 69.9 | 66.9 | 64.5 | **61.0~62.1** |
| 16 | 70.5 | 67.4 | 65.0 | **61.7~62.7** |

- 원시 기록의 팔 이름 `H1 only`·`H1+H2` 는 프로토타입 때 붙인 것으로 각각 셋째·넷째 칸이다 — carry H1(down 을 `leave_norm` 에 접기)은
  한 것이 아니고, 넷째 칸이 H2 의 사이트당 −2 발사다(게이트는 up 대신 down 발사에 탄다). 레인 두 팔은 출력 복사 한 발사를 더
  가졌다(프로토타입 하니스). 접기는 같은 곱(skinny GEMV 의 같은 타일)의 네 발사 산술과
  **바이트 동일**(mixed·inject 모두, 모든 행·up 타일 다섯), cuBLAS 사이트와는 BF16 한 단계(max 0.0021~0.0055).
- `q38site-0919b` 는 엔진 코드(`gated_residual.mix` → `mix_rows`) 그대로: 부팅의 qualify 가 먼저 통과(게이트 잔차 max 0.0063 / rms 0.0027,
  밴드 0.05 / 0.02; skinny_gemv 세 모양 ≤ 0.0028), 바이트 동일 재확인. **시간은 못 읽는다** — 프로덕션 경합으로 두 팔 모두 213~221 µs(평소의 3.3 배).

## 3. 스텝 — `q38stepab-0919a/b/c` ([a](q38stepab-0919a.json) [b](q38stepab-0919b.json) [c](q38stepab-0919c.json))

`probes/engine_qwen38_step.py --lanes qwen38_step_ab`: 층 집합 넷을 served / mm(skinny GEMV 표를 비운 이전 레인) 두 팔로 번갈아. K=3, max_seqs 4.

- **0919a: 8 빌드 모두 캡처에서 사망** — `static_m12` 컴파일 직후 illegal address. 3 행 × 4 토큰 = 12 행의 정적 MoE 발사가 `route_local`
  경로에서 패딩 없이 나갔다(#1192 의 패딩은 전역 경로에만). **#1203 로 고쳐 머지**; 0919b·c 는 8 빌드 모두 캡처.
- **0919b(라우터 + down 만 skinny):** 안정한 집합([4,5,6,7]·[4,5])에서 4 행 검증 타깃이 층당 약 35 µs, 드래프트 그래프 54~172 µs 짧다.
- **0919c(라우터 + H2 접기):** [4,5,6,7] served 빌드는 경합(드래프트도 7.1 ms, 다른 집합은 4.5)이라 뺀다. 나머지 셋에서 4 행 검증 타깃
  −40~−94 µs, 드래프트 −17~−251 µs. 부품 수치(라우터 −14 µs, 사이트 −4~−6 µs × 2, 층당)와 맞게 **스텝당 약 −1.3 ms**(C=1).
- 층 집합 [7]·[1] 은 경합으로 드래프트가 두 배까지 흔들린다 → 네 미지수 풀이(`step`)는 이 날 쓸 수 없다. 같은 빌드 쌍을 직접 비교했다.

## 4. 스텝이 무엇으로 되어 있나 (K=3, C=1, 0919b [4,5,6,7])

- **어휘 헤드**: deep_gemm FP8 약 780 µs/호출(159 MB, 약 200 GB/s) × (검증 1 + 드래프트 체인 3) ≈ **3.1 ms/스텝**. 드래프트 그래프 4.47 ms 중 2.33.
- MoE micro 약 150 µs/층(4 행), W4A8 dense 약 64 µs/층, 믹서 두 사이트 약 120 µs/층.
- 드래프트 그래프의 `aten::gather`(vectorized_gather_kernel) 84 µs × 3 — 호출 자리는 `q38where-0919a` 에서 못 찾았다(프로파일러 스택 빔).

## 5. 안 잰 것

- 플릿 스텝(통신 포함)과 tok/s — 창 금지. 스텝당 −1.3 ms 는 단일 GPU 계산+발사 몫이다.
- 품질 브래킷 — 라우터 점수와 믹서 곱의 마지막 비트가 cuBLAS 와 다르다(합산 순서). 오라클 밴드(qualify)만 판정했다.
