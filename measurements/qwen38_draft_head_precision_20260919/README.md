# Qwen3.8 드래프트 헤드 정밀도 — W8A16(활성 BF16) 채택, BF16 헤드·IVF 근사 헤드 기각 (2026-09-19)

srv4 단일 GPU 레인, 프로덕션 옆, 랭크 3 의 실가중치(헤드 62,080 행 × 4,096, FP8 block-128, 159 MB).
**드래프트 argmax 의 일치율과 발사 시간이다 — 수용률·tok/s 주장 없음(창 필요).**

운영자 원칙(같은 날, PR #1235): 기본은 NVFP4, 비용이 작고 수용률 영향이 큰 곳에 정밀도를 투자한다.
드래프트 헤드의 활성(행)을 FP8 로 양자화하던 것을 BF16 으로 둔다 — 가중치는 같은 FP8 바이트, 읽는 양이 같다.

## 무엇을 바꿨나

- `kernels/dense/fp8_rows.project_bf16`: BF16 행 × e4m3 가중치(블록 스케일). 가중치를 BF16 으로 정확히 넓혀 128 폭 K 블록마다
  BF16 텐서코어 dot, 블록 스케일을 곱한다. `project` 와 같은 바이트, 활성 양자화 발사 하나가 없다.
- `Qwen38Net.draft_logits` → `draft_tokens`: 드래프트(K=3 체인의 관측·체인 스텝)만 이 경로. 검증 스텝의 헤드(`head_tokens`)는 그대로 FP8 행.
  헤드가 cuBLAS 판독이거나 16 행 초과·CPU 면 검증 스텝과 같은 `head_local`.
- 드래프트가 수락되는 조건은 타깃의 키 추첨과 같은 토큰이므로 드래프트는 argmax 가 최적 — 드래프트 쪽에 `decodable` 절단은 없다(기본 디코딩도 없음).

**BF16 기준 상대 오차(같은 티켓, 랜덤 행):** served FP8 행 0.036~0.041, W8A16 **0.025~0.028**(−27~−35%). argmax 일치(BF16 과)는 이 입력에서 둘 다 1.0
(16 행 0.875 는 셋 다 같음). 실측 틈은 아래 쿼리 분포 쪽이 보여 준다.

## argmax 일치율 — `q38ivf-0919d` (쿼리 4,096 개, BF16 헤드 argmax 기준)

| 쿼리 | FP8 행(지금까지) | **W8A16** |
|---|---:|---:|
| token (헤드 행 + 잡음: 한 토큰이 뚜렷) | 99.98% | 99.98% |
| mixture (몇 토큰의 섞임) | 99.37% | 99.10% |
| gaussian (무작위: 1·2 등이 가까움) | 91.77% | **93.46%** |

1·2 등이 가까운 쿼리에서만 차이가 난다(+1.7 pt). mixture 의 −0.27 pt 는 4,096 개 중 11 개 — 잡음 폭. 실제 드래프트 쿼리 분포는
드래프트 쿼리 탭(`--tap-draft-queries`, PR #1232)으로 창에서 캡처해야 알 수 있다.

## 기각 1 — BF16 드래프트 헤드

가중치까지 BF16 이면 랭크당 318 MB 를 드래프트마다 읽는다: 드래프트 argmax 3 번 × (+~680 µs) ≈ **스텝당 +2.1 ms**. 위 표에서 W8A16 이
FP8 과 BF16 사이 틈의 대부분을 이미 닫고, 남은 틈은 1% 안팎이다. 운영자 "알았어 그렇게 해"(W8A16 만).

## 기각 2 — IVF 근사 드래프트 헤드(`--draft-index`, PR #1226, 기본 끔 유지)

|---|---:|---:|---:|---:|
| 512/8 | 5.49 | 3.4% | 52.6% | 2.0% |
| 512/32 | 14.09 | 14.0% | 56.9% | 17.2% |

재현율(정확 argmax 와 같은 비율)이 3~29%(token)·53~60%(mixture). 발사는 71~86 µs 로 전체 헤드 689~696 µs 의 1/9 이지만, 이 재현율이면 드래프트의
절반 이상이 틀린다. 헤드 행이 균형 k-means 로 잘 안 모인다(4,096 차원, 62K 행). 실제 쿼리로 다시 볼 여지는 탭에 남긴다.

## 곁 기록 — BF16 전문가 드래프트 그래프 비용 `q38mtp-0919e` (#1237 트리, 층 [4,5], 50 재생)

K=3 드래프트 그래프(관측 + 체인 둘), µs:

| 팔 | 1 행(블록 6) | 1 행(블록 43) | 4 행(블록 43) |
|---|---:|---:|---:|
| **served = dense BF16 + 전문가 BF16(기본)** | 4,288 | 4,432 | 4,930 |
| 전문가 NVFP4(#1235 이전) | 4,256 | 4,338 | 4,301 |
| 전문가 FP8(export) | 4,272 | 4,279 | 4,557 |
| dense W4 | 3,890 | 3,973 | 4,581 |
| dense FP8 | 4,089 | 4,226 | 4,811 |

C=1 에서 BF16 전문가는 NVFP4 와 같다(+32 µs), C=4 에서 +0.63 ms(4 행은 전문가 여럿을 읽는다). 이 트리의 드래프트 헤드는 FP8 행
(`_fp8_rows` 3 발사 2,031 µs). `mtp_forward(rows=)` 는 다섯 팔 모두 전 행 계산과 바이트 동일(`hidden_equal`, `streams_equal`).

## 안 잰 것

수용률 전부 — dense BF16 + 전문가 BF16 + W8A16 헤드를 함께 켠 부팅에서 pos-1 수용률과 tokens/step. 창이 필요하다.
