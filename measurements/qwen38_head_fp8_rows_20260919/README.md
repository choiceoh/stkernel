# Qwen3.8 어휘 헤드 — 디코드 행을 한 발사 FP8 GEMV 로(`dense/fp8_rows`), 호출당 −190~−200 µs (2026-09-19, srv4 단일 GPU 레인)

> 그대로 두는 기록 — 이 날의 헤드 티켓 넷. 플릿 창 없음. 뒤 실행은 이 파일을 고치지 않고 새 기록을 남긴다.

K=3·C=1 스텝은 랭크의 헤드(62,080 × 2,560 FP8, 159 MB)를 네 번 읽는다 — 검증 한 번, 드래프트 체인 세 번. 스텝 인구조사
(`measurements/qwen38_decode_gemv_20260919`, q38stepab-0919b)에서 deep_gemm 약 780 µs/호출, 스텝의 약 3.1 ms 였다.
`probes/engine_qwen38_head.py`(`--lanes qwen38_head`): CUDA 그래프 8 호출, 팔 인터리브, 무작위 가중치(`per_block_cast_to_fp8`, ue8m0).

## 3. 무엇이 같고 무엇이 다른가

- 입력은 deep_gemm 과 **같다**: 행의 block-128 e4m3 양자화(2 의 거듭제곱 스케일, `dense/fp8.quantize`)와 가중치의 128×128 블록 e4m3
  (ue8m0 스케일). 다른 것은 FP32 합의 순서뿐 — 출력은 BF16 한 단계 안에서 움직인다.
- deep_gemm 호출은 GEMM 말고도 스케일 변환 커널들(`transpose_and_pack_fp32_into_ue8m0` 등)을 매번 돌린다 — 위의 deep_gemm 시간은 그것을
  포함한 호출 전체다. 스텝 인구조사의 드래프트 그래프에서 이름을 못 찾은 `aten::gather` 84 µs × 3(Python 호출이 아님, TorchFunctionMode
  로 확인)도 헤드 호출마다 하나라 이 경로의 것으로 보인다 — 다음 인구조사에서 사라지는지로 확인한다.

## 4. 안 잰 것

- 스텝 인구조사(단일 GPU)·플릿 스텝 — 스텝 몫은 호출당 차이의 곱셈이다.
- 품질 브래킷 — argmax 가 무작위 가중치의 모든 행에서 같았을 뿐, 실제 로짓의 동률 근처는 안 봤다.
