# Qwen3.8 leave — 합의 PDL 종속 + 대기 중 down projection L2 프리페치 (carry H4): 사이트당 −7~−17 µs (2026-09-19, srv4 단일 GPU 레인)

> 그대로 두는 기록 — 캐리 H4 의 GB10 판정과 원시 로그다. 뒤 실행은 이 파일을 고치지 않고 새 기록을 남긴다.

**커널 컴포넌트 시간이다. 엔진·플릿 속도 주장은 없다(D17).** 프로브 `engine_kernel_check.py --lanes qwen38_leave`
(`probes/engine_qwen38_leave.py`). 장치 NVIDIA GB10, 이미지 `st-engine:glm53`(Triton 3.7.1), 프로덕션 옆 단일 레인.

## 왜

#1269 의 스텝 프로파일(C=1 K=3)에서 TP 통신이 스텝의 21% 다(GLM 8%). 합 하나는 one-shot consumer 가 자기 패킷을 발행한 뒤
다른 세 랭크의 패킷을 약 20 µs 기다리는 시간이 대부분이고, 그동안 메모리는 논다. GLM #473 은 그 대기 동안 다음 MHC 의 불변
가중치를 준비했다(C=1 −0.54 ms). Qwen3.8 의 믹서는 세 발사로 나뉘어(`leave_norm` → `down_gates` 6.6 MB → `up_mean` 6.6 MB)
leave 에는 준비할 가중치가 없다. 그래서 leave 를 합의 PDL 종속으로 띄우고, 대기 동안 그 사이트의 down projection 을 L2 로
미리 읽는다(`gated_residual.leave_norm(pdl=, prefetch=)`).

## 무엇을 쟀나

GPU 하나에는 다른 랭크가 없다. 그래서 합을 흉내 낸 커널을 쓴다. 이 커널은 선행 발사를 기다리고, dependent 를 곧바로 풀어 준 뒤
(consumer 는 발행 뒤 푼다), WAIT µs 동안 논 다음 합을 쓴다. 사이트 하나는 다음 순서다: 대역 합 → `leave_norm` → 믹서
(`gated_residual.mix`, 두 발사). 한 그래프에 16 사이트를 넣고, 가중치는 64 MB 넘게 돌려 L2 밖에서 읽게 했다. 팔은 라운드마다
순서를 뒤집으며 번갈아 15 라운드 돌렸다. 팔 다섯 개:

- `off`: 합 뒤에 보통 발사.
- `pdl`: 합의 PDL 종속.
- `prefetch 2 MB` / `4 MB` / `all`: PDL 에 더해 down projection 을 각각 2 MB, 4 MB, 전부(6.6 MB) 미리 읽음.

**바이트 먼저:** 3 ms 늦게 도착하는 합을 NaN 위에 두고, eager 와 캡처 재생 모두에서 스트림·정규화 스트림·믹서 출력이 `off` 와
바이트가 같은지 봤다.

  그래서 기본값은 `PREFETCH_BYTES = None`(전부), `lanes.LEAVE = "prefetch"` 다.

## 무효 실행 — `q38leave-0919a` [원시](q38leave-0919a.log)

같은 프로브의 첫 실행이다. 바이트는 모두 같았다. 시간은 쓸 수 없다. 다른 세션의 4노드 MTP 학습이 srv4 GPU 를 96% 쓰는
동안 돌아서, 사이트가 약 210 µs 로 부풀고 분포가 두 봉우리였다. 그래서 프로브에 분포(min/p25/중앙값)와 GPU 사용률 기록을 더한 뒤
다시 돌렸다.
