# C=2 스텝을 두 요청 스레드로 나누면 — 분할의 페널티 8~23 ms 대 숨길 몫 ≤3.8 ms (2026-09-16)

**기각.** C=2 의 16행 합동 배치를 요청별 8행 스레드 둘로 어긋나게 돌리는 설계(S1 반 층 오프셋, S2 스텝 디커플)는
한 랭크에서 잰 페널티 쪽만으로 죽는다. 프로덕션은 그대로다.

운영자 "c=2 동시성 배수를 개선할만한 아키텍처 개혁" → 인터뷰로 고정한 목적: **bench-dec 고정 길이 팔의 C=2 합산 디코드
tok/s**(T2 단축), 제약 C=1 비회귀 + D10. 허용 레버 L1(그룹 교환 숨김)·L4(고정비), S2 는 열어 둠, L2(적응 K)·L3(전문가
정밀도)는 범위 밖. 운영자의 비유 — 1코어 1스레드와 1코어 2스레드 CPU 가 다른 설계이듯 C=2 에 맞는 설계가 있을 것이다 —
를 이 엔진에 대응시키면: 공유 실행 유닛 = dense 가중치 패스와 공유 전문가(합동 배치가 이미 나눠 쓴다), 스레드별 상태 =
KV·KDA 링·드래프터 링(이미 행 단위), **채울 수 있는 스톨 = 두 스레드가 락스텝이라 같이 멈추는 패킷 비행과 스텝 꼬리**.
그 스톨을 채우려면 스레드를 어긋나게 해야 하고, 어긋나는 순간 dense 가중치 패스와 런치가 두 번이 된다. 이 기록은 그
두 번의 값이다.

## 숨길 수 있는 몫 — 프로덕션 전송의 자기 숫자

원샷 전송이 부팅마다 재는 집합통신당 지연(`OneShot._sample_latency`, 16개 사슬 캡처 재생, 랭크 자기 이벤트; 2026-09-16
프로덕션 부팅 `docker logs st-glm53`):

| 셀 | µs |
|---|---:|
| sum_8rows (C=1 검증 합) | 31.7 (p90 32.7) |
| sum_16rows (C=2 검증 합) | 45.5 (p90 45.9) |
| sum_32rows | 74.7 |
| max_8keys | 13.7 |

행에 비례해 느는 것은 와이어(0.22 µs/KiB, `st_c2_oneshot_consumer_20260915` 의 바닥 0.24~0.29 와 같다). 커널 주석(19차)은
45.5 µs 중 **38.7 µs 가 피어 플래그 대기**라 적었다. C=2 스텝의 패킷 교환은 약 83회(publish 38.9 + moe_packets 29.2 +
oneshot 14.6, `st_decode_profile_c2_20260915`)이므로 S1 이 양쪽을 다 숨겨도 **≤ 83 × 45.5 µs ≈ 3.8 ms**, 어텐션 쪽만이면
≈ 2 ms 다. 그리고 그 대기는 `k_publish_packets` 안에 있다(소비자가 아니라 발행 커널이 피어를 기다린다) — 한 스트림에서
숨기려면 발행/대기를 가르는 프로토콜 변경(2개 비행, 링 4칸)이 먼저 필요했다. 아래 페널티가 그 변경을 무의미하게 만든다.

## 무엇을 어떻게 쟀나

- **레인.** srv4 단일 GPU 레인, rank 3 실가중치, 티켓 `c2threads-0916`(23:03 GO, 8분), 커밋 `d263c317` = main `a40046f4` +
  이 프로브. `probes/engine_prefill_chunk_profile.py --lanes decode,timeline,threads`. 집합통신은 항등, 라우팅은 합성(이
  랭크 어휘 조각의 난수 id), 드래프터·prefix 마크 없음, 실행계획은 `ExecutionPlan()` 기본(direct_mhc·deferred_kda·
  fastpaths 등 프로덕션 스위치 꺼짐) — 기존 `decode` 레인과 같은 조건이다. 그래서 **절대 레인 시간은 프로덕션이 아니고,
  같은 조건에서 팔끼리의 차가 이 기록이 재는 것**이다.
- **팔.** 2K 문맥(2,304), K=7, 16회 재생 중앙값, CUPTI 표, 크롬 트레이스 노출(`trace_exposure`).

  | 팔 | 무엇 |
  |---|---|
  | joint16 | 서빙 모양: 두 요청 16행 합동 그래프 |
  | solo8 | 요청 하나 8행 그래프 |
  | split_attn | S1 어텐션 쪽만: 요청별 어텐션 → 교환, FFN 은 16행 합동(gate/up 한 번, MoE 합집합 한 번, 교환 한 번) — `decode_overlap_attn` |
  | split_both | S1 양쪽: `execution.decode_overlap` 에 (0,1),(1,2) 그룹 — 어텐션·FFN 둘 다 요청별 |

  두 분할 팔은 CPU 참조 레인에서 배치 forward 와 비트 동일하다(`tests/test_probe_decode_threads.py`, KDA-only·KDA+DSA).
- **요약.** `python3 summarize.py c2threads-0916-d263c317.json`. 원본 `c2threads-0916-d263c317.json`, 로그 `c2threads-0916.log`,
  크롬 트레이스 넷(25~52 MB)은 srv4 `~/.cache/st/decode-timeline-{joint16,solo8,split_attn,split_both}.json`.

## 페널티는 어디서 오나 — 바이트가 아니라 런치 바닥이다

레인별 스텝당 ms(타임라인 원시 합), 분할 − joint16:

| 레인 | joint16 | split_attn | Δ | split_both | Δ | solo8 | 런치 j/attn/both |
|---|---:|---:|---:|---:|---:|---:|---|
| MoE | 33.61 | 33.49 | −0.11 | 43.47 | **+9.87** | 22.58 | 45/45/90 |
| dense GEMM | 12.95 | 18.98 | **+6.03** | 26.09 | **+13.14** | 14.47 | 365/601/727 |
| other | 1.33 | 3.14 | +1.81 | 3.92 | +2.58 | 1.91 | 354/754/918 |
| mHC | 3.37 | 2.94 | −0.44 | 3.83 | +0.46 | 2.94 | 96/141/192 |
| KDA | 3.47 | 2.76 | −0.71 | 2.75 | −0.72 | 1.26 | 79/158/158 |
| norm/elementwise | 0.67 | 1.25 | +0.58 | 1.33 | +0.66 | 0.71 | 265/556/531 |
| MLA/DSA | 0.77 | 1.16 | +0.39 | 1.17 | +0.40 | 0.59 | 33/66/66 |

- **어텐션 쪽 분할 +8.1 ms 는 8행 커널이 두 번 도는 값이다.** 16행 `mk_gemm2_kernel<2>`(196회 7.9 ms)가 사라지고 8행 전용
  `mk_gemm_input_cta_kernel<1>` 5.8 ms(68회) + `mk_gemm2_kernel<1>` 3.9 ms(134회) + 입력 pack 1.2 ms(90회) + `mk_mhc_ar` 1.8 ms
  가 들어온다. 그런데 dense 가중치는 스텝당 ~1.2 GB(팩 바이트 합)라 273 GB/s 바닥이 4.4 ms 인데 16행 레인이 12.95 ms 다 —
  이 GEMM 들은 **대역폭이 아니라 런치·지연에 묶여 있다**(단독 셀: 0.5 MiB 짜리 `kda.f_b` 가 74 µs = 7 GB/s, 14 MiB
  `kda.in_proj` 가 93 µs = 161 GB/s). 그래서 둘째 스레드가 내는 것은 두 번째 바이트가 아니라 두 번째 런치이고, L2 24 MiB
  가 두 번째 패스를 받아 줘도 이 페널티는 안 없어진다. 어긋난 두 스레드는 SMT 가 아니라 두 배의 런치다.
- **양쪽 분할은 거기에 MoE 를 얹는다.** 분할 MoE 는 두 스레드의 합집합을 따로 스트리밍하므로 1.31배의 전문가 바이트
  (+9.9 ms), dense 는 +13.1. 2·T1 − T2 = 23.9 와 거의 같다 — 층 단위로 갈라도 스텝 둘을 따로 도는 것과 다르지 않다.
- **런치 수.** 1,237 → 2,321 → 2,682. 갭(커널 사이 유휴)은 0.97 → 1.86 ms 로 커지지만 페널티의 주역은 갭이 아니라
  커널마다의 지연 바닥이다.

## 16행 스텝의 구성 — 남는 레버의 지도 (한 랭크, 기본 실행계획)

| 커널 | ms | 런치 | µs/런치 | 비고 |
|---|---:|---:|---:|---|
| MoE static v5 | 33.0 | 42 | 786 | U=48; 단독 셀 8행 178 GB/s, 32행 204 GB/s (273 의 65~75%) |
| `mk_gemm2_kernel<2>` | 7.9 | 196 | 40 | 팩 ~1.2 GB → 바닥 4.4 ms |
| `mk_mhc_ar_kernel` | 3.3 | 89 | 37.5 | 16행 mHC 자체가 37 µs (8행 33) — 점유율 |
| KDA fused_recurrent | 3.2 | 34 | 93 | 8행 30 µs → 16행 93; 이 프로브는 `deferred_kda` 꺼짐(프로덕션 1.0 ms) |
| 라우터 gemv (cuBLAS FP32) | 2.9 | 53 | 56 | 기본 실행계획의 경로. 프로덕션 C=2 프로파일엔 gemv 가 없고 cutlass bf16 0.8 + topk 1.1 |
| LM head deep_gemm | 0.86 | 1 | | |
| MLA | 0.66 | 11 | 60 | |
| topk (sbtopk + bitonic) | 0.62 | 84 | | 라우터 top-8 |

비 MoE 가 ~21 ms 를 ~1,050 런치에 낸다. 프로덕션 C=2(`st_decode_profile_c2_20260915`, 프로파일러 하 59.7 ms)의 대응:
MoE 27.6, mHC 패킷 소비 5.6(68 × 82 µs — 그중 ~37 µs 가 mHC 계산, 나머지가 PDL·대기), dense `mk_gemm2<2>` 9.3(188회),
통신 커널 6.4(발행 커널 안의 피어 대기 포함), KDA 1.0(+0.6), 헤드 2.3, topk 1.1, 커밋 0.6, wide pack 0.6, absorb 0.5.

**이 지도에서 아키텍처(요청·스텝 구조)로 열리는 문은 없다.** 남는 것은 전부 커널·런치 수준이고, 목적(C=2 tok/s)에는
그대로 닿는다:

| 레버 | 기대 (C=2 스텝) | 성격 |
|---|---|---|
| MoE 스트리밍 178~204 → 250 GB/s | −4~−7 ms | 커널(TMA 파이프라인·CTA 점유), 수치 불변이면 GPU 검증 없이 |
| 소형 dense GEMM 런치 바닥: 같은 층의 f_b·g_b·in_proj / q_b·wq_b 를 한 격자로 | −2~−4 ms | 같은 타일 산술을 새 격자 축에 = 바이트 동일 접기 |
| 16행 mHC 점유율 | −1~−1.5 ms | 커널 |
| 라우터 logits+top-8+가중치 한 런치 | −1 ms | Triton, FP32 합 순서 바뀜 → GPU 검증 |
| 패킷 발행 대기 중 L2 프리페치 (`HintArgs`, ST 엔진 미배선; 11차는 서빙과 겹쳐 미측정) | ≤1.5 ms | 플릿 A/B 만이 잰다 |
| S3 `early_observe` | ≤0.5 ms | 옮겨지는 것은 fc 투영뿐(0.5 ms/스텝) — 브래킷 값어치 없음 |

## 한계

- 한 랭크·항등 집합통신·합성 라우팅·기본 실행계획이다. 프로덕션 스위치(direct_mhc, deferred_kda, fastpaths …)를 켠
  절대값은 다르다(KDA 3.2 → 1.0 등). 팔 간 차만 유효하고, 그 차의 주역(8행 커널 두 벌 런치)은 스위치와 무관하다.
- 숨길 몫 3.8 ms 는 프로덕션 전송의 사슬 지연 셀에서 셈한 상한이다. 어긋난 스레드에서 실제로 겹쳐지는 몫은 더 작다.
- S2 의 "꼬리 숨김"(샘플러·드래프터 ~5–7 ms) 은 이 랭크에 드래프터가 없어 못 쟀다. dense 페널티 23.9 ms 가 그 상한을
  세 배 넘으므로 잴 이유가 없다.
- 절대 시간은 프로덕션 옆 공유 노드의 값이다(부팅 draftfc-0916 이 같은 시각 큐에 있었고 이 티켓은 그보다 먼저 돌았다).
