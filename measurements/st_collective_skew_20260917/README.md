# 집합통신 낙오 편차, 다시 재기 — 대기의 절반은 편차이고 그 편차는 스텝당 8회에 있다 (2026-09-17 20:36)

운영자 "tp=4 대기를 줄일수 있는 방법은 없나" → "낙오편차를 어떻게 줄여?" → "해봐" → "srv4만 클럭 제한을
1600에서 1800으로 올리는건?" → "프로브를 옮기자" → "기록 남겨".

## 어떻게

프로덕션 srv2 rank 0, 릴리스 **`3a84c197`**, 라이브 문에서 `op=begin diagnostic=true concurrency=1` 레이턴시
기록을 잡고 64토큰 요청 하나를 흘린 뒤 네 랭크의 CUPTI 디코드 트레이스를 회수했다. 분해는 **09-14 의 도구
그대로**(`st_oneshot_rails_20260914/decompose_trace.py`) — 같은 방법이라야 그때와 비교된다.

레이턴시 기록은 **문을 예약한다**(다른 요청 409). `record.py` 의 본문 전체가 `try/finally` 안에 있고
`finally` 가 abort 를 다섯 번까지 재시도한다. 09-16 에 TERM 당한 프로브가 이 예약을 2분간 붙들어
프로덕션이 409 를 낸 일이 있다. 측정 뒤 문은 200 으로 확인했다.

`run.sh` 가 전 과정을 재현한다. 원본 트레이스는 `decode-traces.tar.gz`(네 랭크 × 디코드 4스텝).

|---|---:|---:|---:|---:|---|

스텝당 총 대기 **약 5.0 ms** 로 09-14 와 같지만 **구성이 다르다**: 바닥 약 2.4 ms, 낙오 약 2.6 ms.
**대기의 절반이 편차이고, 그 편차는 92회 중 8회에 있다.**

같은 부팅의 one-shot 부팅 게이지(`oneshot_latency_us`, rails=2)가 편차 없는 바닥을 따로 말한다:

행 기울기 1.6~1.8 µs/행, 0행 외삽 16~20 µs. 09-14 의 "고정 16 + 64 KiB 에서 14" 와 맞고 `max_8keys` 15 µs 가
고정비를 직접 준다.

## 09-14 대비 — 둘째 레일이 실제로 먹혔다

09-14 는 둘째 레일(#944)의 이득을 **"Arithmetic for the second rail, not a measurement"** 라고 적었다.
같은 방법으로 다시 재니 실측이 붙는다:

| | 09-14 | 오늘 | |
|---|---:|---:|---|
| `publish` 평균 대기 | 38.1 µs | **28.8** | 편차 8.1 → **5.4** |
| `moe_packets` 평균 대기 | 44.1 µs | **36.1** | 편차 12.0 → **9.7** |
| `consumer` 평균 대기 | 97.4 µs | 490.7 | 편차 54.9 → 458.3 |

대량 통신 79회(전체의 86%)는 **편차 5~10 µs** 로 사실상 붙어 있고, 마지막 발행자가 네 랭크에 고루
흩어진다 — 특정 랭크가 늘 늦는 게 아니라 무작위 지터다. **여기는 남은 것이 없다.**

`consumer` 가 나빠진 것처럼 보이는 것은 **조건이 다르다**: 09-14 는 동기 재생, 오늘은
`decode_iterations=4` 인 burst 루프의 실서빙이다. 두 수치를 직접 빼지 말 것.

## 세 가설을 세우고 셋 다 틀렸다 — 트레이스가 전부 기각했다

낙오가 큰 8회에서 랭크 3(= `10.10.10.4`, srv4)이 `consumer` 의 마지막 발행자 23회 중 **15회**다.
srv4 는 "프로덕션 옆 단일 GPU 레인" 으로 지정된 상시 측정 박스이므로, 부하 때문이라는 가설이 자연스러웠다.
**같은 트레이스로 랭크별 일을 세면 그 가설이 죽는다:**

| 랭크 | 노드 | 계산 µs | 전송 µs | 커널 수 | span µs |
|---|---|---:|---:|---:|---:|
| 0 | 10.10.10.2 | 19,348 | 7,250 | 885 | 49,232 |
| 1 | 10.10.10.1 | **20,063** | 7,769 | 886 | 48,847 |
| 2 | 10.10.10.3 | 19,493 | 8,372 | 886 | 49,539 |
| 3 | 10.10.10.4 | 19,681 | **4,243** | 886 | 49,117 |

계산 상대값 {0:100.0, 1:103.7, 2:100.8, 3:101.7}, span {0:100.0, 1:99.2, 2:100.6, 3:99.8}.

- **네 랭크가 ±3.7% 안이고 커널 수는 885/886 이다.** 프로브 부하가 랭크 3 을 느리게 하고 있지 않다.
  오히려 계산이 제일 긴 것은 랭크 1 이다.
- **랭크 3 의 전송 시간이 다른 셋의 절반(4,243)이다.** 늦게 도착한 랭크는 남을 안 기다리므로 전송이 짧다 —
  랭크 3 은 **늦게 오는 쪽이지 일이 많은 쪽이 아니다.**
- 남는 설명은 **레일 위상**이다. `OSAR_RAILS=2` 는 쌍 {0,1}·{2,3} 을 둘째 함수에 얹고 각 랭크는 레일 0 으로
  둘, 레일 1 로 하나를 보낸다(09-14 기록). 배치가 비대칭이면 도착 순서도 비대칭이다. **이 측정으로 확정하지
  않는다** — 레일별 타임스탬프가 없다.

따라서 **프로브를 다른 노드로 옮기는 것은 이 편차를 줄이지 않는다**(원인이 부하가 아니다). 옮기면 대상
박스가 새로 부하를 지고, 원장의 셀 판정이 거의 전부 `srv4 단일 GPU 레인` 기준이므로 측정 기준기만 바뀐다.

## 클럭 캡 — 플릿 전체에 걸려 있고 srv4 만의 문제가 아니다

    /etc/systemd/system/gpu-clock-cap.service   (2026-08-29, 네 노드 전부 active)
    Description=Lock GPU clocks to 1600 MHz (fleet thermal cap)
    ExecStart=... nvidia-smi -lgc 0,1600

`max SM 3003`, `applications(기본) 2418`, 96% 부하 관측 **1573~1592**. 온도는 rank0 60 · rank1 57 ·
rank2 60 · rank3 61 °C 이고 `clocks_throttle_reasons.active` 는 네 노드 모두 **0x0**.

- srv4 만 낮은 것이 아니다. 네 노드가 ±1% 안이고 제일 낮은 순간값은 랭크 1 이었다.
- srv4 는 제일 뜨겁지만 차이는 1 °C 다. 한 노드만 풀 근거가 이 표에는 없다.
- **한 노드만 올리면 srv4 가 플릿에 없는 기계가 된다.** 원장의 셀 판정이 거기서 나오므로 그 순간부터
  µs 비교가 이전 기록과 대조 불가가 된다.
- 캡 자체(1600 대 max 3003)는 **이 기록이 판정하지 않는다.** 운영자가 "fleet thermal cap" 으로 명시해 건
  것이고, 왜 1600 인지·랙 환경이 어떤지는 여기 없다. 올린다면 네 노드 동시에, 온도와 throttle 사유를 보면서.

## 남는 것 — 스텝 경계 2회

편차는 `max64`(1회/스텝, 바닥의 **26배**)와 `gather64`(1.2회)에 집중돼 있고 `consumer` 가 그 뒤를 잇는다.
이 셋은 샘플링·커밋 부근의 **스텝 경계** 집합통신이고, 랭크 0 만 하는 호스트 일(허가·마감·취소 방송·
샘플링, `serve.py`: *"Rank 0 admits, answers and serves /metrics"*)이 그 경계에 앉아 있다. 대량 통신
79회에서는 랭크 0 의 추가 일이 보이지 않는다 — **경계에서만 보인다.**

09-14 는 *"The bounded burst loop has no such boundary"* 라고 적었는데, 이 부팅은 이미
`decode_iterations=4` 인 burst 루프이고 **경계는 여전히 남아 있다.** 그 문장은 이 형상에서 갱신이 필요하다.

## 안 잰 것

- **속도 판정 아님.** step/s 도 수용률도 안 바뀌었고 아무것도 안 고쳤다. 이 기록은 대기의 분해뿐이다.
- **한 번, C=1, 4스텝.** 반복 없음. 09-14 는 3스텝이었다.
- **레일별 분해 없음.** "레일 위상이 도착 순서를 정한다" 는 **가설**이다. 확정하려면 레일 단위 타임스탬프가
  필요하다.
- **랭크 0 의 호스트 일이 경계 편차를 낸다는 것도 가설이다.** 호스트 타임라인을 이 트레이스로 못 본다.
- **클럭 캡을 올린 실험 없음.** 캡의 성능 영향은 미측정이다.
- 진단 기록의 트래픽은 요청 하나(64토큰)다. 긴 컨텍스트·C=2·C=4 는 없다.
