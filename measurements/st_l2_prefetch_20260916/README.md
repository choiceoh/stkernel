# 벌크 L2 프리페치 — MoE 전문가 스트리밍은 더 느려지고, dense v2 GEMM 은 안 움직인다 (2026-09-16/17)

운영자 "MoE 스트리밍 178~204 → 250 GB/s, 소형 dense GEMM 런치 바닥, 16행 mHC 점유율 — 해봐" 의 첫 판정.
세 항목 모두 **커널 산술은 그대로 두고 메모리 요청의 시기만 바꾸는 힌트**(`cp.async.bulk.prefetch.L2.global`, 연속 런 하나에
요청 하나, smem·완료 대기 없음)로 시작했다. 힌트라 수치는 커널 자신의 add-order 바닥이어야 하고, 실제로 그랬다.

## 1. MoE 정적 커널: 기각 (srv4 단일 GPU 레인 티켓 2회, 팔 7개, 전부 정확)

**가설.** 스탬프(`st_c2_moe_chunk_20260915`)는 CTA 하나가 FC1 을 5.0 GB/s, FC2 를 5.5 GB/s 로 스트리밍한다고 했다. 16 KB 스테이지
둘이 비행 중이고 DRAM 지연이 ~6.4 µs 면 32 KB / 6.4 µs = 5 GB/s — Little 법칙과 자릿수까지 맞는다. 링은 못 깊어진다(CTA 의 smem
99 KB 가 다 쓰였다). 38차 §8 의 스레드별 `prefetch.global.L2` 는 128 B 라인당 요청 하나로 요청 수를 두 배로 만들어 3~5% 손해였다.
그래서 **DMA 레인 하나가 스테이지당 벌크 요청 하나**로 n 스테이지 앞의 B 박스(256 청크 위 reform 박스 = 연속 16 KB)를 L2 에
미리 부르면, smem 없이 비행 바이트가 는다는 가설이다. 셀 `l<n>`(FC1·심·FC2 전부), `lf<n>`(FC2 와 심만).

**결과.** B/A/A/B, warm·evicted, 실물 rank 3 가중치·실물 라우터, 요청 2개(16행)와 요청 1개(8행), 단일 층과 3층 사슬.

| 셀 | C=2 단일 | C=2 사슬 | C=1 단일 | C=1 사슬 | 정확성 |
|---|---:|---:|---:|---:|---|
| l2 | +0.7 / +1.3 % | +0.6 / +0.9 % | +1.2 / +0.8 % | +1.2 / +0.8 % | 1 ulp 바닥, BF16 0 |
| l4 | +2.1 / +2.4 % | +1.9 / +2.2 % | +2.1 / +2.2 % | — | 〃 |
| l8 | **+12.4 / +12.2 %** | +11.9 / +11.8 % | +10.6 / +10.6 % | — | 〃 |
| lf2 | +0.2 / +0.3 % | +0.2 / +0.2 % | +0.5 / −2.2 %† | +0.3 / +0.1 % | 〃 |
| lf4 | +0.3 / +0.4 % | +0.3 / +0.4 % | +1.0 / +0.5 % | +0.9 / +0.9 % | 〃 |
| lf8 | +2.2 / +2.1 % | +2.2 / +2.1 % | +2.6 / +2.7 % | +2.8 / +3.1 % | 〃 |

(warm / evicted 의 평균 변화; † 는 대조군 한 표본의 잡음 — 최소값 기준 +0.1 %.) 깊이에 단조로 나빠진다. 원시 이벤트는
`moe-l-0bb8fbf0.jsonl`(티켓 `c2l2prefetch2-0916`, l2·l4·l8), `moe-lf-7b57c7af.jsonl`(`c2l2prefetch3-0916`, l2·lf2·lf4·lf8),
`python3 summarize.py <jsonl>`.

**스탬프가 가설을 어디서 무너뜨렸는지 말한다** (16행, U=80, evicted, 항목당 중앙값):

| 팔 | FC1 µs (GB/s/CTA) | FC2 µs (GB/s/CTA) | 스팬 µs |
|---|---:|---:|---:|
| 서빙 | 121.0 (5.05) | 52.4 (5.47) | 1272.9 |
| l4 | 127.8 (4.78) | 45.3 (6.33) | 1297.6 |
| lf4 | 131.9 (4.63) | 44.6 (6.43) | 1281.3 |

프리페치를 받은 FC2 는 빨라지고(−13~−15 %), **같은 CTA 의 FC1 은 그만큼 느려진다** — FC2 박스만 미리 불러도(lf4) FC1 이 4.63 으로
떨어진다. 즉 이 커널의 48 CTA 는 이미 메모리 경로를 나눠 쓰는 포화 상태이고, 앞당긴 요청은 비행 바이트를 늘리는 것이 아니라
지금 흐르는 스트림에서 대역을 빼앗는다. Little 법칙의 "지연 × 비행" 그림은 CTA 하나에는 맞지만 48 CTA 의 합에는 다른 병목이
먼저 온다. 38차 §8 의 판독(요청률 경로)과 `z` 셀(요청 최소화, −2.5 %)이 가리키던 자리와 같다: **273 GB/s 까지의 남은 20 % 는
발행 시기가 아니라 접근 무늬(128 B 행 세그먼트의 DRAM 효율)의 몫**이고, 힌트로는 안 열린다.

**남긴 것.** 셀 `l<n>`·`lf<n>` 은 파서·커널·프로브에 남는다(프로덕션 레시피에는 토큰이 없어 서빙 불변). 다음 사람이 이 자리를
다시 열려면 접근 무늬를 바꾸는 커널 작업(사전 스위즐 + 1-D 벌크 스테이지, `z` 의 순열 버그를 고친 형태)이 남은 단 하나의 가설이다.

## 2. dense v2 GEMM (`mk_gemm2_kernel`): CTA 슬라이스 프리페치 — 기각 (티켓 `c2densel2-0916`)

**가설.** 16행 스텝의 dense 레인은 196 런치 7.9 ms(노출 6.75 ms)인데 팩 바이트는 ~1.2 GB 라 273 GB/s 바닥이 4.4 ms 다. 트레이스
분포는 런치당 최소 11.8, 중앙 27.5 µs — 1 MiB 짜리 투영이 14 µs(84 GB/s)다. v2 커널의 raw 링은 `MK_NBUF2_DEF=3`, 8 KB 스테이지 둘이
비행 → CTA 당 ~2.7 GB/s 이고, `ksr` 규칙이 한 CTA 에 주는 K 슬라이스는 4 k-블록(32 KB)뿐이라 파이프라인이 정상 상태에 닿기 전에
끝난다. 그래서 CTA 진입 시(PDL 대기 전, 전임 커널의 꼬리 아래에서) 스레드 0 이 자기 슬라이스의 W 와 스케일을 벌크 요청 둘로
L2 에 부른다(벤치 노브 `set_gemm2_l2_prefetch`, 컨텍스트에 값으로 잡혀 그래프마다 고정; 서빙 경로는 0).

**방법.** `dense_cells` 레인, 모든 서빙 경로 대 `_l2` 쌍, 8·16행, 단일·사슬, warm·evicted, 무관용 바이트 게이트.

**결과: 서빙 W4 셀에서 ±1 % 안, 쿼리 쌍과 드래프터에서 손해 — 기각.** 원시 이벤트 `dense-l2-7b57c7af.jsonl`, `summarize.py`.
B/A/A/B 두 괄호의 평균 변화(warm / evicted), `_l2` 대 서빙 경로, 무관용 게이트 전부 통과(바이트 동일):

|---|---:|---:|---:|---:|---:|
| kda.in_proj (ksr 8, 408 유닛) | +0.9 / −0.3 | +0.0 / +0.3 | +0.7 / +1.1 | −0.1 / +0.4 | 48.2 / 124.4 |
| kda.o_proj (ksr 3, 96) | −0.1 / −0.4 | −1.8 / −0.2 | +0.6 / −0.3 | −2.4 / +1.2 | 24.5 / 52.0 |
| mla.o_proj (ksr 3, 96) | +0.0 / +0.3 | −2.1 / −0.5 | −0.3 / −0.0 | +0.1 / +0.3 | 40.8 / 91.1 |

**읽기.** 서빙 셀은 잡음 폭(±1~2 %) 안이다 — 슬라이스 전체를 L2 에 미리 불러도 시간이 안 움직인다는 것은 **이 GEMM 들의
시간이 가중치의 첫 접촉 지연에 있지 않다**는 뜻이다. evicted 대조군이 그것을 다시 말한다: `kda.o_proj` 4.5 MiB 가 52 µs
(88 GB/s), `mlp.gate_up` 12 MiB 가 123 µs(100 GB/s), 그리고 warm(L2 적중)은 그 절반 이하인데도 prefetch 로 evicted 가 warm 쪽으로
안 간다. 남는 후보는 링의 로드가 아니라 슬라이스당 고정 사슬 — x 양자화 프롤로그, ksr 분할의 fp32 부분합 쓰기·되읽기·도착
원자, 에필로그 — 이고, 그것은 m=16 의 `ksr` 규칙(`mk_choose_ksr2`: 96 슬롯을 한 파도에 채우는 규칙, 30차 스윕은 m=8)을 다시
재는 일이다(`set_gemm2(ksr)` 벤치 훅이 있다; fold 순서가 바뀌어 무관용 게이트가 아니라 허용오차 게이트가 필요하다).
쿼리 쌍·드래프터의 손해는 두 리더가 같은 X 를 읽는 셀에서 프리페치 요청이 서로의 스트림을 밀어낸 것으로 읽힌다 — MoE 의 FC1/FC2
와 같은 무늬다.

**남긴 것.** 노브 `set_gemm2_l2_prefetch`(기본 0)와 프로브의 `_l2` 팔은 남는다. 서빙 커널 바이트는 노브가 0 인 한 그대로다.

## 3. 16행 mHC 점유율: 티켓 없이 닫음

`st_c2_mhc_packed_20260915` 의 컴포넌트가 답을 이미 갖고 있었다: 16행 패킷 소비 커널은 **호출당 20.9 µs**(84팩 사슬, warm)이고,
이번 트레이스의 노출 27.6 µs 와의 차 ~7 µs 는 PDL 인계·커널 경계다. 커널 구조는 (청크, 토큰 그룹) 블록 매핑 — 96 상주 블록 =
6 그룹 × 16 청크, 그룹당 토큰 2.7개 — 에 토큰당 ~4 µs 의 꼬리(sinkhorn, 워프 0)가 빈 블록에서 돈다. 16행에서 더 짜려면 그룹 수를
늘려야 하는데 상주 블록은 레지스터가 96 으로 묶는다. 얻을 상한이 호출당 ~5 µs × 84 = 0.4 ms/스텝이라 커널 재작성 값어치가 없고,
진짜 레버는 경계 수(스텝당 ~1,200 런치 × PDL 인계)라 mHC 가 아니라 이웃 커널과의 융합 쪽이다 — 11차가 시도했던 자리.

## 4. m=16 `ksr` 스윕: 규칙이 이미 최적 — 기각 (티켓 `c2ksr-0917`, 16행)

`dense_cells` 의 16행 셀마다 서빙 경로를 `set_gemm2(n)`(n = 1, 2, 4, 8) 아래 캡처한 팔을 붙였다. fold 순서가 바뀌므로
1 bf16 ulp(원소와 텐서 RMS 중 큰 쪽) 게이트다. 원시 이벤트 `dense-ksr-5ec0d03e.jsonl`.

- **서빙 16행 CTA 셀은 강제 ksr 을 거부한다** — `kda.in_proj`·`kda.o_proj`·`mla.o_proj`·`mla.qkv_a`·`mlp.*` 의 `bound` 경로는
  "sixteen-row cells require the ordinary lane's K slices": 그 커널들의 K 슬라이스 수는 레인의 선언 기하라 벤치 훅으로 못 바꾼다.
- **훅이 먹는 경로(generic: 드래프터 두 셀, pair: 쿼리 쌍)에서는 규칙의 선택이 최적이거나 잡음 안**이다. 게이트는 전부 통과
  (최대 1.0 ulp, fold 순서 차).

| 셀 (서빙 ksr) | ksr1 | ksr2 | ksr4 | ksr8 |
|---|---:|---:|---:|---:|
| drafter.gate_up 단일 (2) | +9.5 / −1.3 | +0.0 / +0.4 | +11.1 / +3.0 | +26.9 / +4.6 |
| drafter.gate_up 사슬 (2) | −0.1 / +2.0 | −0.0 / +0.2 | +0.1 / +1.9 | +4.9 / +4.0 |
| drafter.down 단일 (3) | +18.2 / −3.8 | +16.6 / −3.1 | +16.2 / +5.6 | +25.7 / +14.6 |
| drafter.down 사슬 (3) | +18.1 / +12.5 | +5.5 / +4.2 | +9.7 / +6.3 | +11.4 / +6.4 |
| mla.query 사슬 (3+3) | — | +11.9 / +4.8 | +22.2 / +7.4 | +37.0 / +17.0 |

(warm / evicted 평균 변화.) 슬라이스를 줄이면 warm 에서 크게 느려지고 evicted 에서 기껏 −3~−4 %(단일 층, 사슬에서는 +), 늘리면
둘 다 느려진다. 30차가 m=8 에서 고른 "96 슬롯 한 파도" 규칙은 m=16 에서도 옳다. **dense 소형 GEMM 의 남은 시간은 ksr 로도
안 열린다** — 슬라이스당 고정 사슬 자체(x 양자화·부분합·도착·에필로그)가 값이고, 그것은 커널 본문의 일이다(같은 시각 다른
세션의 `c1deep-0917` "deep-ring arm" 이 그 자리를 재고 있었다).

## 5. MoE 셀 `z` 재도전: 저장소 순서 셋이 전부 틀린다 — 배관 문제로 접음 (티켓 `c2z-0917`, `c2z2-0917`)

reform 타일의 B 스테이지 레이아웃(`probes/b12x_reform_layout_print.py`): B1 `S<3,4,3> o ((8,16),(256,1),(1,2))`(128 B 행),
B2 `S<2,4,3> o ((8,32),(128,1),(1,3))`(64 B 행). 호스트 순열을 **바이트 단위 표준 스위즐**(16 B 청크 ^= 행%8 / (행//2)%4)로
두고 스테이지마다 `cp.async.bulk` 하나로 같은 mbarrier 에 같은 바이트를 완료하는 셀 `z` 는 **네 팔 전부 3.3e7 ulps(max|diff|
8.4)로 게이트를 넘었다** — 옛 `z`(니블 단위 순열, 0/3 PASS)와 같은 증상이고, 둘은 서로 다른 순열이다. 그래서 같은 커널에 저장소
순서 셋을 물리는 진단 티켓(`c2z2-0917`, 원시 `moe-z-95588042.jsonl`)을 돌렸다.

| 저장소 순서 | C=2 단일 max\|diff\| | C=1 단일 | ulps |
|---|---:|---:|---:|
| byte (16 B 청크 ^= 행%8 / (행//2)%4, TMA 하드웨어 모드) | 8.39 | 8.51 | 3.3e7 |
| nibble (8 B 단위 ^= (2행+반)%8 / 행%4, DSL 레이아웃의 원소 단위 읽기) | 7.82 | 7.36 | 3.3e7 |
| plain (순열 없음) | 7.80 | 6.96 | 3.3e7 |

**셋 다 같은 자릿수로 틀리고 서로 조금씩 다르다**: 순열은 결과를 바꾸지만 어느 것도 서빙 바이트를 재현하지 않는다 → 문제는 순열이
아니라 벌크 복사의 배관이다. 종이 위에서는 착지 주소(`storage.sB1` 바이트 베이스 + 슬롯 × 16 KB, 1024 정렬), 원본 주소(타일 우선
[E][K/256][N][128 B] 의 e·2 MiB + kt·128 KiB + 타일·16 KiB), 장벽 회계(TMA 박스와 같은 16384 B 를 같은 mbarrier 에 완료)가 모두
맞아 보이지만, GPU 가 아니라고 한다. 다음 사람이 이 자리를 열려면 **smem 덤프 프로브**(장벽 뒤 B 스테이지 16 KB 를 전역에 쓰는
프로브 전용 모드로 TMA 착지 이미지와 벌크 착지 이미지를 바이트로 대조)가 먼저다. 기대 이득이 옛 `z` 의 −2.5 %(MoE 의 ~0.7 ms/
스텝) 상한이라 여기서 접는다. 셀 `z`·`_swizzle_tile_boxes`·`bulk` 섹션은 남는다(서빙 레시피에 토큰 없음).

## 한계

- 한 랭크, 실물 가중치, 합성 행(실물 라우터), 프로덕션 스위치 아닌 프로브 기본 실행계획. 팔 간 차만 유효하다.
- MoE 는 층 3(단일)과 3·4·5(사슬)다. 다른 층의 라우팅 분포는 다르지만 커널은 같다.
- 스탬프 커널은 장벽 하나를 더 가진 핸들이라 절대 µs 는 서빙 핸들과 다르다(비교는 스탬프끼리).
