## 읽기

- **stash 크기와 넓은 빈 정제는 원인이 아니다.** stash 를 1,024 에서 5,824 로 바꿔도 131K 행의 시간이 2% 안에서 같고, 부분빈 분할은 정제를
  없애고도 시간이 같다.
- **시간은 블록 폭에 거의 반비례한다.** 1,024 → 512 → 256 에서 1.52 배, 1.80 배. 긴 행의 비용은 스레드당 원소 처리(빈 계산·원자 합)이고,
  이 커널은 **행 하나를 CTA 하나가 맡아** C=1 의 8 행이면 CTA 여덟 개만 쓴다. `ST_THREADS` 1,024 가 상한이다.
- **HPC-Ops 가 빠른 이유가 그것이다.** SM 마다 CTA 셋의 영속 그리드로 긴 행을 여러 CTA 에 나눠(KV-split) 131K 행에서 바닥의 4.3 배에 머문다.
- **짧은 행에서는 빈 캐시가 이긴다.** 32K 에서 캐시가 시간을 절반으로 줄인다(67.8 → 36.9). 그 영역에서 ST 는 HPC-Ops 의 1.6 배다.

## 무엇을 하지 않았고 무엇이 남나

- 부분빈 분할 커널은 **머지하지 않는다**(정확하지만 이득 0, 코드만 늘린다). 패치만 남긴다.
- 긴 행을 여러 CTA 로 나누는 설계(행별 히스토그램을 클러스터 공유 메모리로 합치는 HPC-Ops 방식)가 남은 길이다. 디코드 11 층 기준 이득은
  문맥 128K 에서 약 0.15 ms/스텝, ~524K 에서 약 1.9 ms, ~944K 에서 약 3.3 ms(합성 분포)라 긴 문맥에서만 의미가 있다.
  HPC-Ops 를 쓴다면 동점 규칙을 낮은 풀 id 로 바꿔야 서빙 집합과 같아진다.
- 실제 인덱서 logits 의 분포로는 재지 않았다.
